Strengths:
- The codebase relies on abstraction of using interface type (controller, model and view interface) rather than implementation of a class, thus it makes it super easy to adapt our code since we can implement the interface and make it still work with our model, controller and view.
- The components of view are also designed based on the idea of composition, like how a view is composed of a frame, and a frame is composed of a panel, which makes the code more modular and easy to debug. Changing the smaller components does not require changing the class that composes it.
- The codebase has good readability with straightforward and clear variable names and method names. The methods follow the single responsibility principle, where they do not try to do so many different operations in one single method, but rather delegate to different methods.

Limitations:
- Certain types are relying on implementation (Grid, Cell and Card are not interface type but rather than class type), which means we need to know the implementation details. Therefore, we requested providers to abstract out the Grid, Cell, and Card, any interface type like model or controller that returns type Grid, Cell, and Card can be used without needing to know their implementation.
- In the view, the provider uses integers as a way to track which hand (Red or Blue) card is drawn from. Since there is only a fixed set of hands or players, it might be better to represent the data as enum instead of integer.
- The ThreeTriosGameFrame and ThreeTriosGUIView are now implementing the same interface ThreeTriosView. Although the ThreeTriosGUIView implements all methods, ThreeTriosGameFrame does not implement all the methods in the ThreeTriosView, thus making certain methods redundant. It would be better to make an interface that shares common methods between the two ThreeTriosGameFrame and ThreeTriosGUIView. Since ThreeTriosGUIView has more methods than ThreeTriosGameFrame, it can implement another interface that extends that common interface.
- In the ReadOnlyModel, some methods like getCardAt and determineWinner is documented to possibly return null. However, in the view, it’s calling the model to determine the winner, then pull out the player color. If determineWinner returns null, it will throw a NullPointerException. We think it should return a Player with an unassigned color instead, or use Optional and return Optional.empty() if there is a tie to avoid null-related errors.
- Initially, the panel in the view adds the mouse listener when it is constructed, so even for machine player, the view still listens to mouse events when it's not necessary, which results in error if you click on window of a machine player. Therefore, we request to move the addition of mouse listener in the panel's constructor to the setFeatures method. As a result, the view only listens to mouse events when the controller needs to listen to the view for human player.
